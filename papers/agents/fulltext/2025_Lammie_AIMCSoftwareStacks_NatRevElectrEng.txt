Abstract

Sections

Analogue in-memory computing (AIMC) is an emerging computational
paradigm that can efficiently accelerate the key operations in deep
learning (DL) inference workloads. Heterogeneous architectures,
which integrate both AIMC tiles and digital processing units, have
been proposed to enable the end-to-end execution of various deep
neural network models. However, developing a software stack for these
architectures is challenging, owing to their distinct characteristics —
such as the need for extensive or complete weight stationarity and
pipelined execution across layers, if maximum performance is to be
achieved. Moreover, AIMC tiles are inherently stochastic and hence
introduce a combination of stochastic and deterministic noise, which
adversely affects accuracy. As a result, existing tools for software stack
development are not directly applicable. In this Perspective, we give an
overview of the key attributes of DL software stacks and AIMC-based
accelerators, outline the challenges associated with designing DL
software stacks for AIMC-based accelerators and present opportunities
for future research.

Key points
• Analogue in-memory computing (AIMC)-based accelerators,
comprising AIMC tiles and digital processing units (DPUs), can be
used to perform end-to-end execution of deep learning (DL) inference
workloads, with low latency and high energy efficiency.
• The large-scale adoption of AIMC-based accelerators demands
efficient techniques and tools for the co-design of software and
hardware, in addition to sophisticated software stacks, which abstract
the deployment of diverse deep neural network (DNN) models.
• AIMC-based accelerators based on non-volatile memory have unique
attributes, such as fixed weight stationarity and noise arising from
analogue computation, and these have a substantial impact on how
software stacks are developed for them.
• In most work on memory devices for AIMC or the design of
AIMC-based accelerators, the complexity of DL software stack
development and, consequently, the amount of time required are
given insufficient consideration.

Introduction
In recent years, driven by increases in computational capability and by
architectural innovation, modern deep learning (DL) inference workloads have become widespread. Although general-purpose processors, namely central processing units (CPUs), can be used to perform
DL inference, they are relatively energy-inefficient and suffer from
performance issues. More specialized programmable parallel processors — for example, graphics processing units (GPUs) — are much
more performant for highly parallelizable workloads; however, achieving optimal performance with them comes at the cost of high power
consumption and reduced energy efficiency1. To achieve maximum
performance and energy efficiency requires customized hardware
accelerators, carefully designed to optimally execute end-to-end DL
inference workloads2.
An emergent class of customized hardware accelerators relies
on the paradigm of in-memory computing (IMC), which addresses
the processor–memory dichotomy in modern computing systems.
Certain computational operations, such as matrix–vector multiplication (MVM), are performed in place in the memory itself by
exploiting the physical attributes of the memory devices3. Current
state-of-the-art GPUs achieve >5 tera operations per second per watt
(TOPS W−1), for example ≈8.35 TOPS W−1 for an NVIDIA H100 NVL at
400 W, and edge tensor processing units4 achieve 2 TOPS W−1 at 2 W.
In contrast, recent IMC prototype chips have been shown to achieve a
sustained >10 TOPS W−1 (refs. 5,6) for certain DL workloads, and heterogeneous architectures are projected to achieve >50 TOPS W−1 (ref. 7),
highlighting their strong potential for addressing the increasing energy
overheads of modern DL workloads1.
IMC architectures can be broadly categorized as digital IMC
and analogue in-memory computing (AIMC). For digital IMC, the
multiply–accumulate (MAC) operation associated with MVM operations is implemented using digital logic gate-based multiplier and
adder circuitry; for AIMC, analogue currents are accumulated during operation. Digital IMC and AIMC based on static random-access
memory (SRAM) are mature enough for near-term commercialization.

However, a notable limitation is that SRAM-based arrays lack the density to store all the weights of most deep neural networks (DNNs)
on a single die within practical chip area constraints. Hence, weight
reloading is typically performed as a result of limited weight capacity.
A potential solution is to transition to non-volatile memory technologies, such as resistive memories (including resistive random-access
memory and phase-change memory) or flash memory, as they offer
much higher memory density than SRAM. The central component of
such an AIMC-based accelerator is the AIMC tile. AIMC tiles arrange
compute units in a crossbar topology. In one implementation, the
conductance of each device can be modulated to represent specific
weight values8. During MVM operations, inputs are applied as voltages
through digital-to-analogue conversion, while the resulting currents
accumulate. These currents are converted to digital outputs using
analogue-to-digital conversion. AIMC enables constant-time computation that is invaluable in applications requiring high throughput,
such as DL inference.
Although AIMC tiles enable the highly efficient realization of MVM
operations to perform end-to-end execution, there is a need to support
additional operations associated with DL inference9–12. This motivates
the use of a heterogeneous architecture (Fig. 1a) that complements
AIMC tiles with various digital processing units (DPUs). Depending on
the desired performance and flexibility, these can be general-purpose
processors or highly customized digital compute units13. It is also critical to seamlessly integrate these processing units (AIMC tiles and DPUs)
with a high-bandwidth digital communication fabric9.
Figure 1b shows the typical life cycle of a DNN model: among the
critical components are DL software stacks. From the point of view
of a typical end user performing offline inference or serving a model,
DL software stacks automate and abstract the steps required to deploy
diverse DNN models to specific hardware back ends, which execute
the model. For customized hardware accelerators, this is problematic,
because specialized firmware and software must be developed for integration with existing DL software infrastructure — and the complexity
of this task and the effort required are often overlooked. Consequently,
in this Perspective we focus on the challenges and future research
directions related to DL software stacks for AIMC-based accelerators
adopting a weight stationary data flow. We delineate the composition
of these software stacks, offering insights into their unique design considerations. Critically, we emphasize that, although AIMC-optimized
software stacks share foundational principles with stacks designed
for other custom hardware accelerators, the distinct operational and
architectural requirements of AIMC necessitate nuanced adaptations
that pose challenges for infrastructure reuse, and underscore the need
for customized development and a robust and engaged open source
community.

Overview of deep learning software stacks
In this short overview, we answer two critical questions: what is the
objective for DL software stacks, and what are their inputs and outputs? We describe the composition of DL software stacks, introduce
the concept of intermediate representations (IRs) and highlight the
importance of feedback-directed optimization (FDO). We also discuss
how pre-existing frameworks and tools can be used to accelerate DL
software stack development.

domains. The output of a DL software stack is machine code that configures the hardware and executes the DNN model. The configuration

structure or encoding of data, used in the design and implementation
of compilers, that serves as an intermediary between the input and the
generated machine code15. IRs can take various forms, such as parse
trees or abstract syntax trees, but in the context of DL model compilation we refer to an IR as an arbitrary sequence of related operations,
which can be represented using a directed graph. To clearly distinguish
between high-level IRs used to define models in tensor-based frameworks and those used for compilation, we will refer to the former as
computational graphs and the latter as IRs.
Each IR enables the definition of new operations, as well as attributes and types16, which can be used, for example, to specify the iteration
space or the types and access patterns of the inputs and outputs for a
specific operation. IRs can be defined at different levels of abstraction,
with varying degrees of hardware specificity. As an example, at one
level of abstraction, a fully connected layer can be represented using
transpose, matrix multiplication and broadcast element-wise addition operations. At another, loop unrolling can be performed, and the
matrix multiplication operation can be decomposed into a sequence
of dot-product operations with hardware specificity, such that the
utilization of the underlying hardware is maximized by the loops.
‘Dialects’ are used to group different IR objects into a common
declarative region. Within these regions, commonly referred to as
namespaces, transformations and operations that can be performed
on the IR, valid IR operator types, attributes, traits, interfaces and
passes — that is, sequences of transformations and operations — can
be defined as objects. Hence, a dialect can be considered a superset
of an IR in the sense that it extends an IR with additional constructs
while adhering to the IR’s infrastructure and principles. Although these
definitions belong to exactly one dialect, definitions from different
dialects can coexist at any level of abstraction of an IR at any time. The
decomposition from one dialect to another at a lower level of abstraction is referred to as ‘lowering’; multiple lowering steps involving one
or more dialects are referred to as a ‘pass’. Figure 2b shows the lowering
of a simple DNN model comprising a single linear layer, represented
using two tensor-based dialects, to a linear algebra-based dialect and
an arithmetic-based dialect. These can be further lowered and interfaced with tools such as LLVM, to be used to perform machine code
generation. (LLVM and other related tools will be discussed in greater
detail below.)
At a high level, DL software stacks comprise a front end, to which
inputs are fed for processing, and a compiler, which generates machine
code. Although these terms are inconsistently used in the literature,
the front end usually refers to the high-level application programming interface or an interface where users provide a DNN model,
data-processing pipelines and optional retraining logic (for example,
quantization-aware training). We adopt this definition. We consider
the compiler as being responsible for transforming and optimizing
the model from a high-level IR to optimized, low-level machine code.
Compilation can be performed statically, prior to execution (‘ahead
of time’) or during execution (‘just in time’). Hybrid approaches are
also becoming popular: these support dynamic and auto-regressive
computation by statically compiling and generating machine code
for different network components and scenarios, and are stitched
together using just-in-time compilation logic. This kind of flexible
approach is inspired by recent work in other domains that combines
both ahead-of-time and just-in-time compilation approaches17.
Finally, there is the back end. In the literature, at times, the back
end is stated to perform computational graph optimizations15, which
use symbolic reasoning to improve computation efficiency, model

transformations and overall execution performance. Additionally,
it is stated to perform a number of passes on the model IR. These optimizations and passes progressively introduce hardware constraints
and optimize the DNN model for deployment on the underlying
hardware — eventually generating executable machine code which
contains sequences and loops of instructions and routines in a directly
interpretable form by the underlying hardware. We consider the back
end as being solely responsible for providing the execution environment for the machine code, enabling it to interact directly with hardware resources. In other words, the back end ensures that the machine
code knows how to run on the specific hardware it is assigned to, and
provides the tools to execute the code efficiently and effectively.

Feedback-directed optimization
The ideal scenario for deploying a model is a one-shot process, in which
all necessary steps — such as hardware mapping, schedule optimization
and machine code generation — are performed only once. However, in
reality, strong interdependencies between deployment stages make
this difficult. Decisions such as operator mapping and placement
onto processing units affect scheduling, memory access and machine
code structure, leading to non-linear and unpredictable performance
outcomes.
Heuristic-based optimization alone is often insufficient18, as it
cannot fully capture the complexity of these interactions. Instead,
a dynamic feedback mechanism is essential for refining decisions
iteratively. Full-scale evaluation after every design choice is impractical for large-scale DL inference, especially with just-in-time compilation. Therefore, FDO is used to explore design choices — such as
operator placement and precision settings — while balancing trade-offs
such as accuracy, power consumption and throughput19. FDO is performed by introducing optional feedback loops between different
compilation steps; the loops typically use proxy models or estimation tools to quickly approximate the impact of the decisions made
at different steps.

Existing frameworks and tools
There exist numerous frameworks and tools, which can be extended
to support different hardware back ends. For all these frameworks,
computational graphs and IRs are critical to their operation, acting
as a bridge between DNN models and machine code. We categorize
existing frameworks and tools into two distinct categories: first, frameworks that can be used to define DNN models, and the tools that can
convert between them; and second, frameworks and tools used for
model compilation. We also discuss MLIR (Multi-Level Intermediate
Representation), an innovative software infrastructure specifically
designed to support compiler development.
The most popular frameworks for defining DNN models are
PyTorch14, TensorFlow20 and JAX. Although these frameworks share
similar layer and function primitives and operate at comparable
levels of abstraction, converting DNN models between them remains
a complex challenge. This difficulty arises from key differences in
their underlying architectures, execution paradigms and application programming interface designs. For example, PyTorch’s eager
execution model contrasts with TensorFlow’s historic reliance on static
graphs, and each framework also has distinct layer definitions, default
settings and hardware-specific optimizations. These differences
make direct conversion between models nuanced and have driven
the development of standardized, universal IRs21,22, with the Open
Neural Network Exchange (ONNX) format being the most prominent.

These universal IRs aim to act as intermediaries that enable interoperability across the computational graphs of different frameworks, simplifying model conversion by translating high-level framework-specific

Among the most popular frameworks and tools that can be used to
perform compilation, Apache TVM is an open source DL compiler stack
that relies on an IR called ‘Relay’23. TVM performs a series of transformations on this IR, such as algebraic simplifications, loop unrolling and
memory optimizations, and finally lowers the IR into machine code.
Through this pipeline, TVM supports a wide range of hardware back
ends, including CPUs, GPUs and customized hardware accelerators.
The LLVM Project is a collection of modular and reusable compiler
and tool-chain technologies24, and is commonly used by other frameworks, including TVM, for low-level IR optimizations and machine code
generation. Tensorflow XLA (Accelerated Linear Algebra) is Google’s
framework for optimizing and compiling DL models, particularly those
created in TensorFlow, and uses an IR tailored for Google’s tensor processing unit and other hardware accelerators. For CPU and GPU back
ends, XLA uses LLVM for low-level optimization and machine code
generation. Glow (Graph Lowering for Optimized Wireless) is a compiler
framework designed by Meta25. It serves as a machine learning-oriented
layer on top of LLVM, leveraging LLVM’s mature compiler technology to achieve high performance and flexibility. Glow uses a two-step
compilation approach: first, it compiles neural network models from
high-level frameworks into a hardware-agnostic IR specific to Glow
that it can optimize. Once Glow has optimized the IR, it then leverages
LLVM’s back end for the final lowering process, translating the optimized IR into machine code for specific hardware back ends. NVIDIA
TensorRT is a high-performance DL inference optimizer and run-time
library developed by NVIDIA, specifically tailored for NVIDIA GPUs26.
OpenVINO is a toolkit developed by Intel that accelerates DL inference
across a wide range of Intel hardware27. It is designed with a particular
focus on applications involving computer vision and edge computing
and supports various Intel platforms, including CPUs, integrated GPUs,
vision processing units and field programmable gate arrays. One of
OpenVINO’s strengths lies in its model optimizer, which pre-processes
and streamlines the model before it reaches the inference engine, applying optimizations that reduce computation and memory overhead.
The optimized model is then run on the OpenVINO Inference Engine,
a run time that dynamically selects the best execution strategies for the
available Intel hardware.
All of the aforementioned compilation frameworks and tools operate using one or more central IR, containing a complete set of instructions which can be modified and extended. Motivated by the lack of
standardization between the different stacks, and the need for seamless
translation to machine code, MLIR16 was developed to offer a standardization of the compiler infrastructure by providing a unified interface to define dialects. These dialects help represent computations
across multiple levels of abstraction — from high-level DL operations to
low-level machine code generation. This allows developers to optimize
computations at the most appropriate level, whether refining algorithmic operations for domain-specific needs or tailoring machine code
to leverage the unique features of customized hardware architectures.
By unifying these abstraction levels within a single framework, MLIR
not only streamlines the compilation process but also enhances efficiency and performance in ways that traditional, rigid compiler designs
cannot. This disruptive infrastructure has fundamentally changed
how many recent compilers have been designed and developed
(for example, XLA), and is becoming increasingly widely adopted.

Key attributes of AIMC-based accelerators
The following key characteristics of AIMC-based accelerators add
complexity to the development of DL software stacks.

Co-location of heterogeneous processing units
In AIMC-based accelerators, DPUs play a crucial part in handling operations that AIMC tiles cannot execute, such as activation functions and
attention computations for transformer-based models. Additionally,
DPUs can extend the effective model size by managing portions of the
model that exceed the weight capacity of AIMC-based accelerators.
Another important use of DPUs is accelerating small MVM kernels when
execution on AIMC would be slower, or supporting MVMs for which
analogue noise sensitivity is a concern28. There are a broad range of
DPU types, from general-purpose core-based units that accelerate a
wide range of operations to more specialized units, for certain specific
operations, that are optimized for lower latency9,13,29.

Noise
AIMC introduces both deterministic and stochastic noise, which
affects its accuracy. Factors such as memory device stochasticity,
temporal and thermal conductance drift, inaccuracies in analogue-todigital and digital-to-analogue conversion, and IR drop can introduce
error in AIMC tiles. Deterministic noise sources, such as quantization
noise, can be modelled exactly a priori — meaning that prior to deployment, their impact on accuracy can be evaluated and can be guaranteed during operation. By contrast, only the average and variance
behaviour of stochastic noise sources can be modelled30, and although
the effect of these on accuracy can be mitigated using different techniques (such as hardware-aware (HWA) training31, post-placement
calibration methods and chip-in-the-loop retraining; Box 1), AIMC tiles
remain unsuitable for particularly sensitive operations. AIMC-based
architectures address this problem by offloading critical operations —
those required to be executed using high-precision computations — to
DPUs. In this configuration, AIMC tiles are utilized for less sensitive
static MVMs, whereas more sensitive static MVMs, along with dynamic
MVMs, accumulations, activations and normalization operations, are
executed on DPUs.

Fixed weight stationarity
Owing to the relatively prolonged time required to program non-volatile
memory devices and their limited endurance32, compared with other
technologies such as SRAM, weight reloading cannot be readily performed during operation. Hence, for most AIMC-based accelerators,
a substantial number (if not the totality) of weights are first transferred and programmed to memory devices, and then computation
is performed. However, DPUs can be leveraged to extend the effective model size by handling parts of the model that exceed the weight
capacity of all the AIMC tiles. Reprogramming AIMC tiles is time and
energy-inefficient, but DPUs can efficiently fetch weights from memory,
meaning that they can be used to reload weights, at the cost of reduced
performance and efficiency.
To achieve optimal performance when weights are stationary,
pipelined execution across layers is required (inter-module parallelism, where each layer or group of layers is considered a module). For
instance, during the first pipeline step, for the first batch, the first layer
is executed; for the second pipeline step, for the first batch, the second
layer is executed, and for the second batch, the first layer is executed;
and so on. Additional scheduling modifications are required to effectively pipeline execution across layers: most existing frameworks

Analogue-to-digital domain conversion
To implement an MVM operation using an AIMC tile, numerous steps
must be performed. First, for each row of the input matrix, values must
be transformed (scaled, clipped and quantized) to an appropriate
range. Typically, a pulse-width modulation or binary voltage driver is
used to send voltage pulses to each word line (row) of the AIMC tile and
currents are accumulated across each bit line (BL) (column). Based on
the active weight region, different word lines and BLs must be activated.
These analogue currents are then converted back to digital values
using analogue-to-digital conversion. Affine scales and offsets are
applied to compensate for non-idealities and the resulting values are
transformed to another appropriate range and numerical format for
further processing33. The final transformation scale, which typically
can be merged with the affine scale, is a product of the input, weight
and conductance ranges. All of these steps can be orchestrated using
a reconfigurable local controller to avoid excessive communication
overhead, but this introduces a control hierarchy, which increases the
complexity of generating machine code.

Inter-tile and intra-tile weight mapping
Mapping weights to AIMC tiles is non-trivial, because both the tile location in relation to DPUs as well the physical location of mapped weights
within a tile affect performance. For the former consideration, the
weights of larger layers can be distributed across multiple tiles, but
this introduces additional communication and aggregation penalties —
particularly if the tiles, or the DPUs used to perform aggregation, are not
located in close proximity to each other. In the latter situation, within a
tile, the inference of different weight regions can be parallelized if they
have non-overlapping row and column regions. If two weight regions
share the same input, their inference can also be parallelized, by mapping them adjacently. If a tile is under-utilized, then the performance
of the accelerator is negatively impacted. Conversely, if many weight
regions from different layers are mapped to the same tile, pipelining
across input batches becomes increasingly difficult. Finally, weight
duplication can be performed to improve throughput, at the cost of
increased area and power.

Calibration scales
In addition to the aforementioned affine scales and offsets, there are
numerous other calibration scales, which must be determined before
DL inference can be performed. Some of these are specific to each hardware instance (such as the gain of each analogue-to-digital converter)
and can be calibrated using synthetic data, then fixed for different
network deployments12. Others are network-specific (for example,
the input range of each AIMC tile) and must be determined a priori or
during compilation, after the layer weights are mapped.

Deep learning software stacks for
AIMC-based accelerators
The key blocks that make up DL software stacks for AIMC-based accelerators (Fig. 3) are not dissimilar to those for customized heterogeneous
accelerators. The extent of the modifications needed to adapt existing
infrastructure, for the components within each block in Fig. 3 to be
reusable with AIMC-based accelerators, varies considerably. Although
most blocks are shared with a standard DL software stack, some require
substantial modifications.

Before computational graph acquisition and optimizations can
be performed, numerous HWA model adaptations are required to
account for hardware-specific characteristics and training adaptations. As an example, additional HWA training (Box 1) is often required
for pre-trained floating-point networks owing to deterministic and
stochastic noise sources. For some hardware architectures, at the same
time, calibration scales (such as those required for affine correction)
can be learned using back propagation. Modification of network
weights and pruning can be performed at different stages with varying degrees of supervision, for example, during training with labelled
data (quantization-aware training) or post training (post-training
quantization). In either case, the behaviour of these steps is governed
by information in the provided system definition. The co-location of
heterogeneous processing units necessitates heterogeneous mapping
of layers to AIMC tiles and DPUs. This can be performed using simple
heuristic-based28 or more sophisticated approaches34.
As discussed earlier, computational graph optimizations are a
core ingredient of any DL software stack. After computational graph
acquisition, formal mathematical techniques, including algebraic
manipulation, are leveraged to perform optimization. These transformations are then applied to improve performance metrics, conserve
computational resources and streamline model calculations. Key transformations include expression simplification, dimension inference and
shape optimization, and operator fusion — which entail the reduction
of complex expressions to simpler forms, avoidance of redundant
reshaping operations and combination of multiple operations into
compound operations.
Traditional IRs need customization to support hardware-specific
features of heterogeneous accelerators, such as extensive or complete
(fixed) weight stationarity, and inter-tile and intra-tile weight mapping. High-level IR optimizations are then performed to implement
hardware-specific templates to perform operator fusion, transformations and graph reconstructions. These transformations are also used
to lower a layer-based IR to an operation-based IR, on which low-level IR
optimizations are performed. These optimizations include placement,
post-placement calibration, memory management and scheduling
steps. Mapping entails the association of one or more operations to
a type of processing unit, whereas placement entails the assignment
of a mapped operation to a processing unit at a specific physical location. Chip configuration refinement steps are performed to improve
accuracy by tuning some scales and parameters using prior hardware
information or feedback from the hardware directly. Memory management and scheduling determine the sequence of operations during
execution and how different memory hierarchies, such as caches,
are utilized.
Finally, an optimized, operation-based IR is converted into
machine code tailored for the AIMC-based accelerator. This machine
code encompasses control sequences and commands for both primary
operations and low-level routines, for example, analogue-to-digital
domain conversion. The increased diversity of AIMC-based hardware architectures can introduce challenges during this step, as traditional compiler back ends assume a general-purpose instruction
set architecture (ISA). For AIMC-based hardware architectures with
finite state machine (FSM)-driven control logic, specialized compilation techniques, such as microcode generation or hardware description languages, may be required. More complex architectures with
coexisting FSM-driven control logic and ISA-based execution models
require FSM-controlled operations to be aligned with ISA-driven execution, which needs careful scheduling and control flow management.

To balance model complexity and computational feasibility,
a hybrid proxy modelling approach can be adopted, combining
lightweight analytical estimations with selective simulation-based
validation. This strategy mitigates the risks of oversimplification by
employing efficient proxies for routine assessments, whereas detailed
simulations validate predictions for critical decisions. For instance,
regression-based models predict latency and energy consumption on
the basis of the input size, precision settings and layer characteristics,
enabling rapid yet reasonably accurate estimations. Two main components should be considered: model features and hardware attributes.
Model features include layer dimensions, sparsity levels and precision
settings — these directly influence computational cost and memory
access patterns. Hardware attributes include the number of AIMC
tiles, noise sensitivity, conductance variability and analogue-to-digital
conversion precision, as well as DPU capabilities such as computing
precision and memory bandwidth.
Surrogate modelling techniques, such as Gaussian process regression and Bayesian optimization, help balance accuracy and computational cost by efficiently exploring the design space on the basis
of prior performance observations. Multi-fidelity models dynamically

switch between low-fidelity estimates and high-fidelity estimates on
the basis of optimization stage and decision criticality. By integrating
these estimation techniques directly into the iterative feedback loops
of FDO, the software stack can dynamically adjust mapping, placement
and precision settings, ensuring a balanced trade-off between accuracy,
power efficiency and throughput. This hierarchical proxy modelling
approach ensures computational feasibility while enhancing the noise
robustness of large-scale models such as large language models (LLMs).

Research opportunities
AIMC-based accelerators are actively being developed, and building
robust DL software stacks for these accelerators is crucial to fully realize their potential. A robust and engaged community is also needed,
for innovation and long-term sustainability, and can be encouraged
through open source initiatives, educational resources and community
engagement.
Topics associated with the design and development of DL software
stacks for AIMC-based accelerators are promising and highly impactful
areas for research. To this end, numerous future research directions
can be pursued, which we group into the following five broad themes.

Hardware integration and ecosystem development
The adoption of AIMC-based hardware accelerators for DL depends on
their seamless integration into existing frameworks such as PyTorch
and TensorFlow. Well-documented back-end integrations enable transparent execution and simplify compiler tool development. Similar
to how Google’s XLA is optimized for tensor processing units and
NVIDIA’s TensorRT for GPUs, achieving deep integration would allow
machine-learning engineers to experiment with AIMC-based accelerators, fostering innovation and improving system-level performance
and model accuracy.

Intermediate representations, optimization and
compiler tools
Existing IRs for DNN models with weights mapped to AIMC tiles lack
widespread adoption and consistent use across different compilation
tools. This is due to use of closed source tools, hardware-specific proprietary representations and the need for multiple dialects at different
compilation stages. A major challenge is to balance abstraction and hardware specificity. High-level IRs enhance portability but lack fine control,
whereas low-level IRs are optimized but less generalizable. A hierarchical
IR structure with a well-defined lowering process is ideal. Open source
efforts are crucial to standardizing IRs for AIMC, with frameworks such
as MLIR providing a strong foundation. However, further work is needed
to develop pattern-matching libraries and portable optimizations,
fostering a unified ecosystem for AIMC-based accelerators.
For AIMC-based accelerators, during compilation, steps that govern placement, routing or scheduling — for example, the mapping of
DNNs to processing units — are highly interdependent. As a result,
decisions made in one step influence the constraints and the achievable
performance and accuracy in others. For instance, optimal mapping
may increase communication demands, requiring careful placement
and routing; poor placement or excessive data traffic can cause scheduling conflicts. Achieving a near-optimal solution often requires iterative

refinement or the use of joint optimization strategies to balance these
interdependencies.
Another research topic is inter-layer pipelining. Most DL software
stacks are designed to perform intra-layer parallelism, in which one
layer is executed at a time, and the same processing units are reused
for different layers. Adapting these stacks to support the pipelining
of different input batches across layers is challenging, as it deviates
from the standard execution model. Although some compilation tools,
such as the Pipeline Executor in Relay, have introduced experimental
support for this type of pipelining to accommodate emerging custom
hardware accelerators, the functionality remains in its early stages.

Placement, scheduling and routing
During compilation, the implications of data movement between AIMC
tiles and DPUs must be taken into consideration — particularly with
regard to the impact on placement, scheduling and routing. As the
resulting design space is extremely large, most previous work9,35–37
has focused on one of these three aspects, while making simplifying
assumptions about the others. Taking into account the interdependency of placement, routing and scheduling is non-trivial, and although
some works have explored this using accurate simulation-based
tools38–40 and analytical models35,36, integrating such approaches into
a DL software stack for AIMC-based hardware and evaluating their
effectiveness remains an open area of research.
Additionally, to achieve optimal performance when weights are
stationary, pipelined execution across layers as well as within a layer is
required — that is, intra-module and inter-module parallelism. In a fully
weight stationary accelerator, input tensors should enter the system
such that when the first vector finishes with the first layer (or the first
part of the first layer), another can immediately take its place while
the first vector continues its journey through the spatially mapped
network. To achieve such a stall-free pipeline, balancing the number of
operations across the layers may also be necessary — for example, by
replicating the weights of a small but heavily used layer, such as small
convolutional kernels.

HWA model adaptations and refinement of chip configuration
To achieve satisfactory DNN accuracy, a combination of HWA training,
post-placement calibration methods and chip-in-the-loop retraining is
crucial for AIMC-based accelerators. Libraries for HWA retraining and
other HWA model adaptions on AIMC-based architectures exist but
require extensive hyperparameter tuning and manual intervention,
making automation difficult. This complexity arises from the large number of additional hyperparameters and constraints introduced during
retraining, which increase sensitivity to scale and weight perturbations.
Unlike quantization-aware training, HWA retraining provides robustness
against non-idealities that are non-deterministic and potentially evolving over time. It is also computationally expensive, especially for large
models or when heterogeneous mapping is involved. Although some
progress has been made to simplify the process and increase training
speed41, HWA retraining remains challenging, with major work needed
to make it more efficient and automated. Post-placement calibration
methods42 help mitigate accuracy loss caused by mismatches between
the assumed hardware during HWA model adaptations and the actual
hardware used for deployment. Their main advantage is avoiding the
need for costly iterative HWA retraining during the compilation process.
In contrast, chip-in-the-loop retraining43,44 directly compensates
for device non-idealities by performing on-chip MVMs during forward propagations and updating the devices using the accumulated

Model serving

Finally, developing a DL software stack requires careful consideration of the programming mode and model-serving scenarios. Offline,
single-user model serving is straightforward, but serving multiple
users, handling asynchronous requests or distributing execution across
accelerators adds complexity. Existing frameworks can manage distributed execution and online model serving but often require access
to the hardware’s internal state, making integration challenging.
Serving LLMs poses unique challenges owing to their large size
and the need for efficient key-value cache management to support
low-latency, high-throughput inference. Frameworks such as vLLM
and TensorRT-LLM optimize memory and inference but require further improvements to fully support heterogeneous accelerators and
enhance the workload distribution across accelerators.
