Yimin Wang , Graduate Student Member, IEEE, Zhen Wu , Graduate Student Member, IEEE,

Abstract—Large Language Model (LLM) inference challenges
memory/computing organization and dataflow optimization on
traditional hardware stacks due to its various attention mechanisms and autoregressive structure. In-memory computing (IMC)
and near-memory computing (NMC) architectures have emerged
as potential solutions to reduce the memory burden in LLMs.
However, efficient LLM orchestration on IMC/NMC, as well as
dedicated IMC/NMC architecture optimization, are interrelated,
encompassing a hardware-software co-design space of a myriad of parameters, which still remains largely underexplored.
This work provides a joint architecture-dataflow exploration
(JADE) framework that covers both architectural factors on
computing/memory/communication, and algorithmic factors on
LLM dataflow. We identify key configurations in four categories:
computing and memory organization, interconnection topology,
matrix multiplication (MM) unrolling and mapping, and attention mechanism. A unified MM representation enables flexible
unrolling and mapping on various architectural organizations.
Dataflow is routed based on the collective communication patterns inherent in the distributed LLMs and the features of
common topologies. Finally, case studies show the design tradeoffs
between key design options and provide insights into both
homogeneous and heterogeneous IMC/NMC design for LLMs.
Index Terms—Large language model, in-memory computing,
near-memory computing, design space exploration, heterogeneous architecture.

II. P RELIMINARIES
A. IMC/NMC-Based Accelerators
Recent commercial LLMs, such as GPT [26] and the Llama
series [27], [28], [29], [30], are predominantly decoder-only
Transformers, as shown in the top left of Fig. 1. Each decoder
layer comprises an attention layer and fully connected layers,
which spawn a series of successive MMs and matrix-vector
multiplications (MVMs). Despite the pre-trained weights, successive MMs/MVMs generate a large amount of intermediate
dynamic data. In this paper, we name the matrix multiplication
(A · B) with a dynamic matrix A and a static matrix B
as Dynamic-Static Matrix Multiplications (DSMMs) and that
with both dynamic matrices A and B as Dynamic-Dynamic
Matrix Multiplications (DDMMs). The DSMMs and DDMMs
are empirically assigned to IMC and NMC, respectively, as
shown in Fig. 1.

Existing memory-centric dataflow exploration frameworks
[15], [16], [17], [18], [19], [20], [21], [23], [24] are predominantly tailored for NNs and fall short in addressing the
challenges of LLMs. This is exacerbated by several key challenges: i) LLMs require a flexible allocation of MMs between
IMC and NMC based on the stationarity of data; ii) LLM
inference exhibits significantly different matrix sizes and cache
access patterns between the prefill and autoregressive decode
stages; and iii) matrix partitioning in LLMs increases the
number of partial results that need to be aggregated by an
order of magnitude due to the substantial size of the matrices
involved.
Though prior works have shown IMC/NMC-based systems for LLM acceleration, most only support model-specific
dataflow with custom architectural design [5], [6], [7], falling
short in terms of system and dataflow flexibility to diverse
models. AllSpark [11] and Energon [12] focus on the transformer mapping and scheduling on an NMC-only array
organized homogeneously in the 2D mesh topology. LEAP
[10] presents a 2D mesh array architecture with evenly
distributed IMC and NMC resources with dataflow and parallelism optimization for LLM acceleration. HALO [8] studies
the transformer scheduling on the chiplet level to minimize the
inter-layer communication overhead while the dataflow and
architecture within a chiplet is unexplored. Theseus [13] and
WaferLLM [14] propose design solutions for wafer-scale LLM
accelerators with conventional digital computing units, lacking
support of the emerging IMC or NMC elements.
Hence, this work is motivated to explore the hybrid
IMC/NMC LLM accelerator design in an extended design
space that covers flexible computing/memory/communication
organization on various levels. The comparison of this work
with existing works is shown in Table I. The previous works

B. Design Space Construction
We classify the key design factors into four categories,
which span across the hardware hierarchies. We consider the
hardware organized in two levels: core and tile [13], as shown
in Fig. 2, where the core hosts the elementary IMC or NMC
unit, and the tile comprises an array of IMC or NMC, which
is used for a layer or a partial layer.
1) Computing and Memory Organization: We specify the
differentiated setup for IMC and NMC on both the tile and core
levels: the system can be tile-level homogeneous and corelevel heterogeneous (referred to as homogeneous architecture
HO), or tile-level heterogeneous and core-level homogeneous
(referred to as heterogeneous architecture HE), as shown in
Fig. 2. A core can be dedicated to either IMC or NMC units
(core-level homogeneous) or host both IMC and NMC units
(core-level heterogeneous).

2) Interconnection Topology: Mesh and tree topologies
are considered for intra-tile connections, given their common
applications in multi-core architecture and memory organization, respectively. This work only considers the tree topology
in connecting IMC tiles, where the broadcast and reduction can
be efficiently performed on different hierarchy levels. Whereas
the DDMMs in NMC feature more point-to-point communications, which do not suit the tree topology. Therefore, the
architecture under consideration is confined to HOMM, HEMM,
and HETM, as shown in Fig. 1, where the last two letters stand
for the intra-tile interconnection topology for IMC followed by
that for NMC resources.
3) Attention Mechanism: This category considers the attention type and kernel fusion options. Common attention types
are multi-head attention (MHA) and grouped-query attention
(GQA). In traditional MHA, each K/V head has a corresponding Q head. In GQA, K/V heads are shared in a group of
Q heads, which intends to reduce the burden on computing
and memory overhead. The kernel fusion mechanism, e.g.,
FlashAttention [31], was originally developed to minimize
the off-chip memory access on the GPU when performing
attention layers. In this work, we evaluate its effectiveness on
the IMC/NMC-based systems.
4) MM Unrolling and Mapping: Unrolling and mapping the
matrices onto the IMC or NMC cores is critically important in
the array-based accelerators, interrelated to the data reuse and
reduction. We unify the unrolling of both DDMM and DSMM
into multiple nested loops, and correlate them to the hardware
dimensions in both mesh and tree topologies.

The framework runs through three main steps after initialization, based on the input files: virtual mapping, physical
mapping, and dataflow generation. The virtual mapping handles the tiling and unrolling of each DSMM/DDMM operation

B. Virtual Mapping
Virtual mapping tiles the large matrices in LLM inference
to manageable sizes and unrolls the multiplication loops onto
an ideal 2D hardware array, before considering the physical
inter-matrix placement in the next step. MM involves two
matrices, and each matrix is partitioned along two dimensions,
which results in three nested loops as shown on the top left of
Fig. 4. The partitioned matrices in each loop can be unrolled
either spatially along the hardware dimensions or temporally
by streaming in.
1) Representation in Mesh Topology: Assuming a 2D array
hardware architecture, the spatial unrolling can align the

horizontal (X) or vertical (Y) dimensions as shown in the
bottom left of Fig. 4. Loop tiling techniques in this paper are
denoted as O|M|I → X|Y|T which represent that the outer
loop, the middle loop, and the inner loop are unrolled spatially along the X, Y dimensions, and temporally, respectively.
This notation aligns with the existing dataflow representation
for convolutions [18]. The tiling size on spatially unrolled
dimensions is determined by the computation and memory
resources in each core. The tiling size on temporally unrolled
dimensions is dependent on the interconnection bandwidth,
which is minimally a single row/column of the tiled matrix
under the bandwidth bound.
2) Representation in H-Tree Topology: Consider a hardware array organized in an H-tree topology with a total of L
levels. At a chosen level L x , there are 4Lx nodes (referred
to as core groups), and each node encompasses 4L−Lx leaf
nodes (cores). In this work, the core groups and the cores
within each group in the H-tree are interpreted as the X and
Y dimensions, respectively, as shown in the bottom right of
Fig. 4. In the hybrid H-tree and 2D mesh topology where
sub-trees are connected by a 2D mesh on top, the mesh serves
as the L x level, which is the X dimension, and the sub-trees
are the Y dimension.
3) Unrolling Categories: Mathematically, there are eight
different unrolling categories based on the possible combinations of spatial (S) or temporal (T) unrolling on the three
loops. S represents spatial unrolling on X or Y, which have
been defined in both mesh and tree topology. The evolution
of the unrolling categories regarding the resource sufficiency
is shown in the top right of Fig. 4. S|S|S stands for the
resource-overprovisioned scenarios, which have been demonstrated in GPU architectures [32], [33]. S|S|T, S|T|S, and
T|S|S (i.e., two dimensions unrolled spatially) are commonly
considered to process hardware arrays with regular 2D topologies. Whereas S|T|T, T|S|T, T|T|S, and T|T|T refer
to resource-limited application cases in which the temporal
unrolling dominates.
4) Stationarity-Based Unrolling Strategy: Due to the different temporal and spatial constraints in IMC and NMC, their
considerations for unrolling are different.
a) DSMM unrolling in IMC: DSMMs appear in the
projection step in the attention layers. They fit well with
the IMC cores due to the stationarity of the weight tensors
WQ , WK , WV , and WO ∈ RD×D , where D is the embedding
dimension. DSMMs adopt the T|S|S scheme when the IMC
resources are sufficient, meaning the middle and inner loops
corresponding to the weight tensors are fully unrolled spatially
along the IMC PE array. Thus, the tiled weight tensors are
stored in the crossbars. The number of crossbar arrays required
by each matrix after tiling is d CD e2 , where D is the embedding
dimension and C denotes the crossbar width/height.
b) DSMM unrolling in NMC: Although NMC mainly
handles DDMMs, it can also support DSMMs when IMC
resources are insufficient. Dynamic matrices in the attention
include Q, K, V ∈ RD×S , and S ∈ RS ×S . While S|S|T,
S|T|S, and T|S|S unrolling can all suit NMC arrays due
to their 2D spatial unrolling, this work considers S|S|T and
T|S|S to keep one matrix stored in the scratchpad in the

C. Physical Mapping
Based on the tiled and unrolled matrices from virtual
mapping, the next step is to physically allocate the spatially
unrolled matrices to certain cores and the temporally unrolled
matrices to certain locations in the memory hierarchy (distributed scratchpad, local buffer, or main memory).
1) Intra-Matrix Mapping: The S in unrolling can be
mapped to X or Y based on the resource availability. When
the available resources on the hardware are insufficient for
the spatial unrolling, the loop can also be unrolled in both
temporal and spatial dimensions (XT or YT), meaning new
data can be fed in temporally but at each time the data are
spatially distributed. In tree topologies, X or Y can be flexibly
fit to the tiled matrix size by adjusting the L x level. In mesh
topologies, the X or Y for each matrix is also dependent on
the core allocation among the different matrices, which is to
be elaborated in the following inter-matrix mapping.
2) Inter-Matrix Mapping: This step determines the relative
placement of the various matrices on the mesh array. The intermatrix placement is not considered in the H-tree since the
sub-trees at the L x level are topologically identical and have no
impact on the dataflow and utilization. Inter-matrix mapping
is also distinct in HE and HO architectures: the inter-matrix
mapping of DSMMs and DDMMs in HE are decoupled due to
the physical separation of IMC/NMC array, whereas that in HO
are coupled to each other. In HO architectures, the inter-matrix
mapping for DSMMs (WQ /WK /WV /WO ) is determined first,
and then the mapping for DDMMs (Q/K/V/O) is aligned to
the region of their weight tensors. This alignment helps direct
K/V cache management in their local region and also avoids
the imbalanced matrix sizes in GQA.
3) Mapping Space Generation: This step is focused on
generating the possible inter-matrix placements on mesh
topologies. It follows three heuristic constraints regarding the
regularity and proximity of the placement: i) Sub-matrices
originating from the same weight matrix must be placed
within a spatially proximate region; ii) This region should
have a rectangular shape to facilitate regular dataflows and
reduce routing complexity; and iii) The sub-matrices within
this region should be ordered in a row-major or column-major
fashion. As shown at the top of Fig. 5, four key factors are
abstracted, and all the possible layouts that satisfy the model
layer size and the available resource limit, considering the
three heuristic constraints, will be generated.

Fig. 5. Inter-matrix mapping design space generation and pruning for mesh

4) Mapping Space Pruning: To enable efficient design
space exploration, this work also includes a pruning step to
further discard the infeasible cases before evaluating all of
them. Two key constraints are considered to determine the
feasibility of a design case. Constraint 1 (C1) is that the
overall aspect ratio of the physical layout on tiles should not
exceed a predefined range. δ is a hyperparameter specifying
the extremum aspect ratio,

aspect ratio is within δ, 1δ can be kept for the subsequent
evaluation. Constraint 2 (C2) is that the adjacency of the
matrices should align with the original operation flow. For
example, the area allocated to Q and K should be physically
adjacent to efficiently perform the QKT calculation, and the O
area should be adjacent to the outward border connecting to
the next layer. Architectural candidates violating either C1 or

5) Kernel Fusion Considerations: We consider both the
attention as originally proposed in [35], which we refer to as
original attention in the rest of the paper, and the kernel-fused
attention known as FlashAttention [31]. The key difference
between them is the total volume of the intermediate matrices.
The complete attention score matrix S ∈ RS ×S needs to
be stored in the original attention, whereas FlashAttention
replaces it with an O∗ ∈ RS ×D . FlashAttention [31] fuses the
two successive MMs–QKT and S0 V into unified nested loops,
which means the matrix S does not need to be stored. In this
work, the original S is stored in the scratchpad of Q, and the
additional O∗ is stored in the scratchpad of O. FlashAttention
originally reduces the amount of data generated at a time in
the on-chip memory of GPUs, and its effectiveness on the
IMC/NMC-based distributed architecture will be discussed in
Section V.

D. Dataflow Generation
The described virtual mapping and physical mapping have
mapped the tiled matrices and intermediate operations spatially and temporally across the array. This introduces extra
communication overhead for broadcasting partitioned input

The overall architecture comprises program memory, control
logic, and a tile array, as illustrated in Fig. 8. The co-processor
populates the program memory with instructions consisting of
three primary components: i) the command, which configures
the operating modes of the core and its associated router;
ii) selection bits, which specify the target tile and core IDs;
and iii) a repetition count, which defines the number of loop
iterations for the current command. To minimize system idle
time, the program memory utilizes a double-bank design. This
allows for concurrent operation: while the main controller
reads and decodes instructions from one bank, the co-processor
programs the other. Based on these instructions, the tile array
is optionally configured into one of three modes: HOMM, HEMM,
or HETM.

we adopt RRAM-based technology [36] as the baseline.
Notably, because the JADE framework focuses primarily
on mapping-dataflow explorations for LLM inference, the
high-level mapping strategies remain independent of the underlying IMC technology. Consequently, the IMC units can be
abstracted as closed boxes within the framework.

memory and multiply-accumulate (MAC) units. The scratchpad stores dynamic data, including K and V, which persist

The architecture supports both inter-tile and intra-tile connectivity. Intra-tile routers integrate local adders to perform
efficient partial-sum reductions at the source as discussed in
Section III-D.
1) Mesh-Based Tile: In tiles utilizing mesh interconnects,
each router features five I/O ports: four for communication
with adjacent routers (North, East, South, West) and one for
the locally attached core, as shown in Fig. 9(a). Incoming data
is buffered in dedicated FIFOs, and specialized reduction units
are included to handle local reduction of partial results.
2) Tree-Based Tile: For tiles employing H-tree interconnects, the routers and links are scaled hierarchically. To match
the throughput requirements of the subtrees, the link bandwidth is halved at each descending level of the hierarchy. For
a subtree containing M leaf PEs, each child-to-parent downlink
consists of M/2 parallel word lines, while the parent-to-child
uplink carries M lanes, as depicted in Fig. 9(b). Likewise,
incoming partial results from child links can be reduced before
being sent to the next router. This H-tree structure facilitates
more deterministic dataflows and reduces the area and energy
overhead associated with large buffers in mesh topologies.
3) Inter-Tile Interconnect: Connectivity between two meshbased tiles is established by linking neighboring routers along
the tile boundaries. When bridging a tree-based tile and a
mesh-based tile, the root router of the H-tree is interfaced
with the mesh router located at the center of the adjacent
boundary. In this configuration, the FIFO buffers within the
mesh router manage synchronization between the two distinct
tile architectures.

patterns.

E. Comparison of Prefill and Decode
This case study focuses on identifying the different bottlenecks in the prefill and decode stages. In HOMM and HEM/TMs,
since the layout of the KV cache in the scratchpads is fixed,
the per-token critical path has the same trend in both the
prefill and decode stages. The critical path reported in Fig. 11
directly translates to the per-token latency in the decode phase,
where the token-level pipeline can hardly be achieved in an
autoregressive manner. However, input token-level pipelining
can be achieved in the prefill stage, resulting in much higher
prefill throughput and the decode phase being the bottleneck.
We experimented on HOMM, which is the best case of critical
path, and prefill and decode throughput in Llama 3-8B and
Llama 2-13B inference are shown in Table III. The gain in
prefill throughput depends on the possible number of pipelining stages. In HOMM, the token-level pipelining happens mainly
in the QKT and S0 V steps, where the packet communication in
the router and computation in NMC between successive tokens
can be overlapped, and the maximum number of pipeline
stages is equal to the number of NMC cores on its critical
path. The imbalance in prefill and decode throughput has
also been observed in GPUs when both stages are colocated
in the computing system [43], [44], necessitating separate
systems for prefill and decode, which will be explored in future
research.
We further compare this work to the state-of-the-art LLM
accelerators in terms of throughput and energy efficiency in
Table IV. These works include wafer-scale accelerators [14]
and IMC-focused work [41], [42]. This work achieves better
performance compared to the previous IMC-based works,

thanks to the hybrid IMC-NMC design catered for both the
dynamic and static data, as well as the dedicated router design.
The throughput of JADE and other IMC-based accelerators
currently lags behind that of wafer-scale systems, primarily due to the vast disparity in total resource provisioning.
However, assuming equivalent wafer-scale provisioning, IMCbased designs may offer a promising path toward surpassing
existing fully digital wafer-scale accelerators in power efficiency. This potential advantage is largely attributed to the
significant reduction in static data movement inherent in the
IMC paradigm.
F. Scalability
The scalability comes in two parts: i) the time cost (e.g.,
throughput/latency) scaling under the varying model sizes and
context window lengths, and ii) the capacity limit on the
maximum model sizes or context window lengths.
1) Model Size Scaling: Regarding the time cost scaling, a
positive observation in this work is that the critical path does
not scale up linearly to the model sizes when the context window is fixed. The critical path is increased by ∼ 2× when the
model size is increased by 8× from Llama 3.2-1B and Llama
3-8B, as shown in Fig. 11. This stems from both how models
scale and the critical path in the proposed architecture. Model
size typically scales along three dimensions: the embedding
dimension, the FFN hidden dimension, and the number of
layers, whose scaling factors are denoted as se , sh , and sl ,
respectively. Under such scaling, the attention and FFN layers
approximately increase in parameter count by factors of (s2e )
and (se · sh ), respectively. When comparing Llama 3.2-1B and
Llama 3-8B, for example, se = 2, sh = 1.75, and sl = 2,
resulting in an overall model size increase of ∼ 8× model.
However, due to the constraints in the inter-matrix mapping,
the critical path for operations such as broadcast and reduction
is primarily determined by the longest horizontal or vertical
communication route. As a result, the critical path scales
approximately with se · sl or sh · sl and not se · sh · sl . To validate
this trend, we compare it to the results reported in [14], which
show similar observations. Regarding the capacity limit, the
overall IMC capacity determines the maximum amount of
model parameters that can be accommodated, and the scaleout solution is necessary once the capacity is exceeded, which
we leave as future work.
2) Context Window Scaling: Scaling up the context window
is challenged by the capacity of the local scratchpad in
NMC tiles, since the size of intermediate data in NMCs
grows with the context window length. Future work might
consider introducing an intermediate memory channel at the
tile level to host efficient intermediate data (e.g., K/V cache)
loading/offloading, so that the NMC tiles would be able to
transfer the K/V cache to/from the main memory by tile-level
data packet hops.
