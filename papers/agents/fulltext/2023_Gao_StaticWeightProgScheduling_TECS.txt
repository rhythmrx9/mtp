Most existing architectural studies on ReRAM-based processing-in-memory (PIM) DNN accelerators assume
that all weights of the DNN can be mapped to the crossbar at once. However, these studies are over-idealized.
ReRAM crossbar resources for calculation are limited because of technological limitations, so multiple weight
mapping procedures are required during the inference process. In this article, we propose a static scheduling
framework which generates the mapping between DNN weights and ReRAM cells with minimum runtime
weight programming cost. We first build a ReRAM crossbar programming latency model by simultaneously
considering the DNN weight patterns, ReRAM programming operations, and PIM architecture characteristics. Then, the model is used in the searching process to obtain an optimized weight-to-OU mapping table
with minimum online programming latency. Finally, an OU scheduler is used to coordinate the activation
sequences of OUs in the crossbars to perform the inference computation correctly. Evaluation results show
the proposed framework significantly reduces the weight programming overhead and the overall inference
latency for various DNN models with different input datasets.

an area-constrained embedded or edge devices (typically dozens of Mbits) is substantially smaller

complexity and weight size of DNNs, the deployment of a DNN inference engine with weight size
larger than the overall PIM capacity will continue to be a common practice in resource-constrained
application domains. A few recent works [16–18] consider the constrained PIM resource, and
propose some scheduling schemes to improve the inference throughput of batched images.
However, utilizing value similarity to reduce the weight programming overhead has not been
discussed.
In this article, our goal is to design a DNN inference framework for practical ReRAM PIM
devices with limited capacity. The framework optimizes the overall inference latency by reducing
the online weight programming latency via statically scheduling the weight deployment. To
achieve this goal, our design principle is to map the model weights to ReRAM cells with OU
granularity and explore the weight value similarity to reduce the programming overheads. The
following challenges need to be addressed: (1) The DNN weight to ReRAM OU mapping should
be re-designed to seek the maximum bit-wise reuse benefits; (2) How to correctly activate OUs at
runtime given the offline generated mapping.
To address the first challenge, we categorize the various writing characteristics of ReRAM
crossbar discussed in the literature work, and conduct empirical studies to identify the potential
impact on the DNN weight programming latency. In particular, we build a model for the crossbar
programming latency considering three important factors including (i) bit-wise SET and RESET
operations; (ii) programming latency variation between parallel executed crossbars; (iii) distance
between OUs and voltage drivers of the crossbar. For the second challenge, in the offline phase, a
scheduling table for each crossbar of every weight programming process is generated, and the activation sequences of the OUs for each inference computation stage are recorded. During the online
inference stage, the corresponding OUs are activated by decoding the value in the scheduling table.

BACKGROUND

2.1 OU-Based ReRAM PIM Accelerator for DNN
Figure 1 shows a typical ReRAM-based accelerator for DNN model [19, 21, 38]. The accelerator
consists of multiple tiles, where each tile consists of multiple processing elements (PE), and
each PE has multiple ReRAM crossbar arrays. During the DNN inference stage, input feature
map data (converted to input wordline voltages) are used to slide over the weights of DNN filters
(pre-programmed to ReRAM cells as conductance) to perform MVMs in the convolution and fully
connected layers.
Numerous ReRAM-based DNN accelerators assume that an entire crossbar array can be activated in a single cycle. However, it has been observed that the accumulated effect of per-cell current deviation on the inference accuracy is non-negligible [36]. Instead, each crossbar array needs
to be operated at a smaller granularity (typically between 8 × 8 and 32 × 32), called operation unit
(OU), to ensure the accuracy of computation. As a result, only one OU on each crossbar array can
be activated in each computation cycle. Similar to recent studies [12, 24–26, 42], we adopt the
OU-based ReRAM PIM architecture in this work.
Figure 2 shows an example of the DNN weights mapping process to OU-based ReRAM crossbar
arrays for a convolution layer. Assume the OU size is 2 × 3, and there are 2 filters of size 2 × 2 × 2.
Each filter weight is of 3-bits precision and is stored in three single-level ReRAM cells (SLC)
across three bitlines. During implementation, the input vector is broken down and sequentially
transmitted to wordlines over multiple clock cycles, while simultaneously decomposing and

ReRAM Programming Latency

The programming latency of ReRAM cells is determined by multiple factors. First of all, it has been
well recognized that a RESET operation takes a much longer time compared with a SET operation
[28, 34, 39, 41]. The bottom left sub-figures in Figure 1 show the crossbar structure and the I-V
characteristics of a typical bipolar ReRAM cell. A ReRAM cell with a low resistance state (LRS)
and a high resistance state (HRS) can represent logic ‘1’ and ‘0’, respectively. Switching a cell

from HRS (logic ‘0’) to LRS (logic ‘1’) is a SET operation which needs a positive voltage, and the
reverse process is a RESET operation which needs a negative voltage with a proper magnitude
which needs significantly longer latency.
Furthermore, the programming procedure of a crossbar wordline also affects the latency. It is
shown that the ReRAM effective voltage decays as the number of selected cells increases [29]. To
prevent the potential write failures due to the effective voltage drops below the RESET threshold
voltage, instead of programming the entire wordline of a crossbar array, a common strategy is
to program the wordline at a smaller granularity of 4- or 8-bit segments [29, 30, 32, 34, 40]. For
example, assume a 512 × 512 crossbar array with 1024 OUs of size 16 × 16, the entire crossbar has
to be programmed at the granularity of 8-bit segments sequentially, leading to 1024 × 16 × (16/8)
= 32,768 programming times. Therefore, the overall programming latency of a PIM crossbar array
is not negligible.
Finally, it has been observed that the distance between ReRAM cells and voltage drivers has significant impact on the programming latency [29]. The resistance switch of a ReRAM cell depends
on the time integral of current. When the delivery path is longer, the equivalent line resistance in
the circuit increases, resulting in higher voltage drops. This, in turn, weakens the current flowing
through the cell. As a result, as depicted in Figure 2, the RESET latency of the cell in OU2 is significantly longer compared to that of OU3. In practice, for a 512 × 512 crossbar array, a latency gap
of up to 70X can be observed for RESET operations on cells with different distances to the voltage
drivers [29].
3 MOTIVATION
Currently, most ReRAM-based DNN accelerators assume the entire weights of a DNN model can
be pre-loaded into the PIM device without any runtime programming overhead. However, while
the technology scaling continues to deliver denser and faster ReRAM-based PIM design, it is still
lagging behind the ever-increasing complexity of DNN models. For example, as presented, with
9mm2 and 21.82mm 2 ReRAM die sizes, the capacity can be only 64 Kb and 158.8 Kb [14, 37], respectively. With the die area increase, the capacity could be improved to several megabytes. Table 1
shows the weights of several common DNN and NLP networks based on 32-bit floating point and
quantized into 8-bit intergers. We observed that these common models have weights of tens of MB
or even hundreds of MB. Even with 4- or 8-bit weight value quantization, it still requires multiple
or even dozens of weight programming stages to complete the inference for a single image on a
ReRAM-based PIM device with practical area constraints (e.g., with 16 Mb or 32 Mb capacity). Even
for MLC ReRAM with higher density, multiple rounds of weight programming (with potentially
larger MLC write cost) are still inevitable under the same area constraint.
In a recent study [18], Lu et al. propose a scheduling framework for weight programming in
the context of area constrained ReRAM PIM for DNN acceleration. However, they only know how
to maximize the reuse of partially loaded weights via scheduling of input feature maps across a
batch of input images. On the other hand, we aim to optimize the programming latency for each
programming cycle by constructing the weight-to-OU mapping with fine-grained modeling of bitlevel programming latency. The two approaches (reuse loaded partial weights and reduce weight
programming latency) are orthogonal and can be combined seamlessly.

4 FRAMEWORK OVERVIEW
With resource-constrained PIM device, the entire size of DNN model weights are much larger than
the available PIM capacity. Hence, the DNN inference process has to be explicitly partitioned into
multiple iterations. In each iteration, only partial weights can be programmed as resistances on the
device. After one iteration, the device resistances need to be reprogrammed with weights belong
to the next iteration, and the reprogramming processes are quite time-consuming as presented
above.
In this section, we briefly introduce the proposed programming latency aware framework for
DNN inference on resource constrained PIM devices. As shown in Figure 4, the proposed framework consists of an offline phase and an online phase. In principle, the offline phase is used to
statically generate the weight-to-OU mappings with minimal reprogramming latencies between
two inference iterations. With the weight-to-OU mapping, the offline phase also needs to maintain
a OU scheduling scheme to coordinate the computation sequence of OUs in one iteration. The online phase utilizes the mapping and scheduling scheme to perform the weight programming and
DNN inference at runtime.
4.1

Offline Phase

The ultimate goal of the offline phase is to mitigate the overall ReRAM written cost of weight
programming stages during the online phase. Since we adopt the OU-based ReRAM PIM architecture for DNN inference as discussed in Section 2.1, the task of the “Weight Allocator” module
is to generate a weight-to-OU “Mapping Table”, which assigns each OU-sized weight block to a
physical OU at a specific inference iteration. In accordance with the discussion in Section 2.2, the
cost of writing an OU-sized weight block to a physical OU depends on various factors including
the existing data stored in the OU as for the previous inference iteration (which determines the
SET/RESET operations required), as well as the relative position of the OU within a crossbar array.
Furthermore, during the weight programming stages at runtime, different crossbar arrays can be
programmed in parallel, while weights blocks within each crossbar array are written in sequential
to the OUs. As a result, in order to minimize the overall runtime weight programming overhead, we
design a search strategy to find a near-optimal weight-to-OU mapping in the “Weight Allocator”

As shown in Figure 2, in the OU-based PIM architecture, the entire weight is partitioned into OUsized weight blocks. Meanwhile, the input feature maps for each DNN layer need to be properly
arranged and converted to input voltages of the corresponding crossbar array. Existing work on

of OUs and corresponding input feature maps are straightforward [24, 36, 42]. On the other hand,
in the above-mentioned mapping table generated by the proposed “Weight Allocator” module, we
allow a weight block to be mapped to arbitrary physical OU in order to reduce the weight programming cost at runtime. To ensure the correctness of DNN inference, we design an “OU scheduler”
module in the offline phase of the proposed architecture. The inputs of the “OU scheduler” are
the DNN model which defines the computation between the input feature maps and the weight
blocks, the PIM structure with crossbar and OU organization, as well as the generated “mapping
table” which contains the weigh-to-OU mapping in each inference iteration. Based on this information, the “OU scheduler” module will generate a scheduling table to guide the activation order
of OUs and corresponding input feature maps at runtime.
4.2

Online Phase

In the proposed framework, the DNN inference process is divided into two iterative sub-stages. The
“Weight Programming” stage prepares partial weights for the subsequent inference stage, subject
to the capacity of PIM device. It writes OU-sized weight blocks to the designated physical OUs
in accordance with the mapping table generated in the offline phase. Note that on a resourceconstrained PIM device where the entire weights cannot be programmed onto the PIM at one go
before DDN inference, the online weight programming cost has to be counted in the end-to-end
inference latency.
The “inference” stage of the online phase starts once the required weight blocks for the next
DNN inference iteration have been programmed onto the OUs. It reads the offline generated scheduling table to activate the computations on OUs with corresponding input feature map data. Similarly as in [36] and [42], we utilize the on-chip buffers in each PE for temporarily storing input
and output feature maps, and accumulating the partial sum of the corresponding filters according
to the type of computation. The “inference” stage and “weight programming” stage are iteratively
executed till the DNN inference completes for each given input data.

As the formula shows, the programming latency of a single OU depends on the number of SET
and RESET operations and its location. The latency of the RESET operation in the OU varies with
the distance between the OU and the voltage drivers. The programming latency of the whole
crossbar is the sum of the programming latencies of all its OUs. Finally, the programming latency
of the whole weight region depends on the slowest crossbar.
When programming weights to ReRAM OUs, two unique intra-crossbar factors of ReRAM need
to be considered: (1) The RESET operations at row-wise of ReRAM cells have more impact on the
programming latency than SET operation; (2) The distance between the OU and the voltage drivers
has a negative effect on the programming latency—the farther the OU is away from voltage drivers,
the longer the programming latency it has. One inter-crossbar factor of ReRAM should also be considered: different ReRAM crossbars are programmed in parallel, so the programming latency for
each weight region is dominated by the longest crossbar programming latency. To minimize the
number of RESET operations, we first propose a similarity-based matching strategy. Its principle is
that when one iteration ends, we will compared the to be programmed weight region with the values of current OUs. The weights are separated into weight blocks according to the size of OU (each
OU stores one weight pattern). The similarity-based matching strategy will try to map these weight
blocks to the corresponding OUs with least RESET operations. To balance the program latency of
different crossbars, we further propose a crossbar balanced mapping strategy. At last, we take the
OU location information into consideration and propose the a distance-aware mapping strategy.

there are any cells in a row of one OU needs to be reprogrammed from 1 to 0 in the next iteration,
the number of RESET operations should be added by one.
In practice, to achieve crossbar balance (make all the crossbars have similar programming
latency), we make the weight region to be programmed as the search space, and use the weight
blocks on OUs to search their most similar successors. The whole matching process is performed
in a greedy approach. As shown in the figure, first, B1 searches the weight block with the highest
similarity from weight region 2, and B8 is selected. In the following searches, B8 is no longer
considered (make B8 in ❷ gray and attached behind B1 in the list of ❸). If a whole logical crossbar
has found enough weight blocks in a certain layer (i.e., Le f t equals to zero), all weight blocks of
this layer in weight region 2 will be kicked out of the search space like B8, as shown in Algorithm 1,
line 16-17. With the process going, we found that the reset operation required for B7 programming
to B3 is equal to 0, so B7 is stored after B2 in the list of ❸. After matching all the weight regions
in this way, every weight block of the first weight region will form a programming list as ❸.
• Balanced Mapping Strategy. The above search process is a greedy process, so the search
space of the OU that is searched first is the largest. As the progress being performed, the search
space would become smaller and smaller, making it difficult to match the ideal weight blocks for
the following OUs. If the matching process is carried out in serial in the way of OU first and then
crossbar, the last crossbar may suffer from huge programming latency. So, we cyclically execute
similarity-based matching strategy between all crossbars. As shown in ❷, to balance the search
space of each crossbar, after B1 in crossbar1 is matched, we will select B3 in crossbar2 for the
matching, then B4, B2, and so on. Through this matching sequence, the programming latency
differences between the crossbars are greatly mitigated.
• Distance-Aware Mapping Strategy. Considering the variances of programming latencies
of OUs in different locations in a crossbar, the OU with the farthest distance (i.e., denoted by
the farthest OU) from the voltage drivers should prioritize the mapping procedure. The working
process that combines the distance-aware mapping strategy and the similarity-based mapping
strategy is as follows: When the search is completed for all weight regions of the DNN model, a
programming list for each logical OU will be generated, as shown in Figure 5 (the length of each list
depends on how many times the neural network needs to be programmed). We calculate the sum
of the number of RESET operations required in each list, as shown in ❸, and adjust the position of
each list inside the logical crossbar. The list with the smallest RESET operations would be placed
at the farthest OU in the logical crossbar, and the list with the largest RESET operations is placed
at the position of the nearest OU, and so on, as shown in ❹. With this approach, we can get the
mapping table for each weight region. The mapping tables of these three weight regions are shown
in Figure 5 ❹. They record the mapping of weight blocks to OUs in each crossbar.
5.2

OU Scheduler

This subsection elaborates the static OU scheduler to support the out-of-order OU activation. In
the original design, the OUs in the crossbars are activated in sequence to perform the inference
process. With the weight mapping strategy which aims to minimize the programming latency,
we actually have broken up the mapping sequence between the input feature map and OUs (i.e.,
weight blocks) on the crossbars.

inference computation latency. Therefore, as long as the pruned weight size is still larger than the
available ReRAM PIM capacity (which is true for all the DNN models in our evaluation), online
weight programming is required for the DNN inference.

6.4 Endurance
ReRAM has demonstrated superior endurance (>1012 [7]). Taking AlexNet as an example, inference
of an input image with 32Mb ReRAM PIM requires 15 iterative weight programming stages at
runtime. Assume a frame rate of 30 input images per second, in the worst case (every cell needs
to be programmed in each iteration), the ReRAM is expected to work continuously for 70 years.
Note that the weight programming cost is induced by the deployment of a relatively large DNN
inference model on a resource-constrained PIM device.
In practice, our proposed method significantly reduces the number of cells that needs to be
programmed in each iteration, which benefits both programming cost as well as the ReRAM endurance. In this section, some neural networks are selected based on a specific ReRAM configuration C2, and the impact of the proposed framework on the programming rate of ReRAM cells is
evaluated, and the results are shown in Figures 5-10. It should be emphasized that the number of
unit operations counted in this experiment is not the number of operations programmed in parallel by multiple units as described in the previous section, but the count is performed on a single
unit basis. In the baseline approach for the ImageNet, CIFAR-10, and NLP tasks participating in the
experiment, to complete all iterations of a neural network inference, an average of 31.05%, 23.62%,
and 36.70% of the units require SET or RESET operations. It is important to note that each unit will
only be executed with either SET or RESET operation, and both operations will not be executed at
the same time. After applying the weight similarity-based DNN inference scheduling framework
proposed in this article to these neural networks, the ratio of units requiring programming operations to complete all iterations of a neural network inference decreases to 22.11%, 17.41%, and
28.12% for the three neural networks, reducing the need for programming operations by 8.94%,
6.21%, and 8.58% of the total number of units in the ReRAM chip, respectively.

7 CONCLUSION
In this article, we identify the challenge of online weight programming cost for DNN inference on
a resource-constrained ReRAM PIM device. A framework consisting of an offline phase to generate weight-to-OU mapping and scheduling information, and an online phase to iteratively proceed
the weight programming and normal inference. The experimental results show that, the proposed
mapping strategies achieve effective weight programming overhead reduction and overall performance improvement for various DNN models.
